# key-concurrency Specification

## Purpose

限制同一分组内每把上游 Key 同时处理的在途请求数，避免单 Key 被打满限流；超限时改选其他 Key，并在进程异常后自动收回泄漏的槽位。

## Requirements

### Requirement: 每 Key 并发上限默认不限制

系统 MUST 将每把 Key 的在途并发上限视为默认不限制（配置值 `0` 表示不限制）。未改该配置时，系统 MUST 保持现有选 Key 与转发行为，不得因为未配置上限而拒绝请求。

#### Scenario: 默认不限制时行为不变

- **WHEN** 分组未配置每 Key 并发上限或配置为 `0`，客户端连续并发多个请求
- **THEN** 系统 MUST 按现有活跃 Key 轮询处理，不得因在途数拒绝或跳过 Key

### Requirement: 全局与分组可配置并发上限

系统 MUST 允许在系统设置中配置每 Key 在途并发上限，并允许标准分组覆盖该值。聚合分组本身 MUST NOT 持有独立的并发上限；一次请求使用的上限 MUST 为实际服务该请求的标准分组（含被选中或被亲和绑定的子分组）的有效配置。

#### Scenario: 仅覆盖的分组生效

- **WHEN** 全局上限为 `0`，管理员将分组 A 的上限设为 `2` 并保持分组 B 未覆盖
- **THEN** 系统 MUST 只对分组 A 的 Key 执行在途限制，分组 B MUST 仍不限制

### Requirement: 超限 Key 被跳过并改选

当有效上限大于 `0` 且某把 Key 的在途请求数已达到上限时，系统 MUST 跳过该 Key，改选同一分组内另一把未达上限的活跃 Key。若所有活跃 Key 均已达上限，系统 MUST 向客户端返回当前「无可用密钥」同类错误，MUST NOT 把请求继续打到已满的 Key 上。

请求结束（成功、失败或客户端断开）后，系统 MUST 释放该次占用的在途槽位。

#### Scenario: 单 Key 打满后改选

- **WHEN** 分组只有两把活跃 Key、上限为 `1`，Key1 已有 1 个在途请求
- **THEN** 系统 MUST 把下一个新请求分配给 Key2，而不是 Key1

#### Scenario: 全部打满时拒绝

- **WHEN** 分组所有活跃 Key 的在途数均已达到上限
- **THEN** 系统 MUST 返回无可用密钥错误，且 MUST NOT 向上游再发新请求

### Requirement: 亲和绑定 Key 超限时临时改选且保留绑定

当渠道亲和性已开启、会话已绑定某把 Key，且该 Key 仅因在途数达到上限而暂时不可用时，系统 MUST 为**本次请求**改选其他未满 Key，且 MUST NOT 删除该会话绑定。绑定 Key 因拉黑、冷却或已移除而不可用时，仍按渠道亲和性的改绑规则处理。

#### Scenario: 绑定 Key 在途满时不拆绑定

- **WHEN** 某会话绑定的 Key 在途数已达上限，该会话再次请求且组内另有未满 Key
- **THEN** 系统 MUST 用其他 Key 完成本次请求，并且在绑定 Key 腾出槽位后的后续请求 MUST 仍优先使用原绑定 Key

### Requirement: 泄漏的在途槽位必须自动收回

系统 MUST 保证在途计数不会因进程崩溃或未配对释放而永久占满 Key。泄漏的槽位 MUST 在有限时间内被收回，使该 Key 重新可被选中，无需人工清缓存。

#### Scenario: 崩溃泄漏后 Key 可再次被选

- **WHEN** 某把 Key 因进程中断留下未释放的在途计数，且已超过系统的收回期限
- **THEN** 系统 MUST 允许再次选中该 Key，不得一直视为已满
